# CodeQ Persistent Project Work Graph — Implementation Roadmap

**Purpose:** turn CodeQ into a persistent project developer that can carry a selected model through a project goal in small, verified steps. This roadmap is the implementation checklist and evidence log. Work phases in order; update this file with source paths and actual test results after each phase. Do not mark a phase complete from design or source inspection alone.

**Scope:** existing local CodeQ project/workspace/run flow. Preserve selected-model behavior, current sandbox/approval boundaries, snapshots, publication safeguards, and other workspaces. Do not add remote-access architecture. The graph UI is an additional CodeQ bottom-panel tab beside Terminal; it must not replace or resize the editor layout unexpectedly.

## Current source baseline (verified 2026-11-11)

- `openagent/codebase/repository.py` scans project files, language/framework and commands, symbols, imports, dependency and Python call graphs, routes, database models, test files, and provides lexical `select_context()` retrieval.
- `openagent/codebase/service.py` persists projects, runs, task dependencies, tool calls, file changes, test runs, events, snapshots, approvals, and memories. Runs create a plan, execute ready tasks, validate, request completion audit and diff review, and publish verified changes.
- `frontend-second/src/screens/WorkspaceScreens.tsx` contains the CodeQ IDE and bottom panels; inspect the current component before adding UI.
- This source baseline is **not yet** a unified project work graph. In particular, durable project requirements, requirement-to-task-to-evidence links, graph-guided retrieval, and a graph panel are not established by the existing structures alone.
- The working tree contains user changes. Each implementation phase must preserve unrelated edits and avoid replacing files from an older snapshot.

## Target behavior

The user gives CodeQ a project goal and chooses a model. CodeQ stores the goal and acceptance criteria, maps them to current project structure, and continues through unblocked work automatically. Each task gets only current, relevant source context. A task is complete only when its configured verification evidence passes. The run/project remains resumable across model calls and application restarts. It ends as **completed** only when all acceptance criteria have verified evidence; otherwise it remains **blocked**, **failed**, or **awaiting approval** with the reason and next action recorded.

## Graph contract

Use one connected, versioned graph model with four user-visible views. Nodes and edges have stable IDs, timestamps, provenance, source hashes where applicable, and freshness state. Derived relationships must be distinguishable from inferred/candidate relationships.

| View | Core nodes | Required edges |
|---|---|---|
| Project | project goal, constraint, capability, acceptance criterion, milestone, completion state | goal requires criterion; milestone contains criterion; criterion is satisfied by verified evidence |
| Code knowledge | repository, file, module, symbol, route, test, config, dependency, command | imports, calls, defines, implements, tests, configures, depends on; include provenance and confidence/source |
| Task | task, subtask, checkpoint, approval | blocks, depends on, addresses criterion, touches code node, produces artifact |
| Evidence | patch/file change, snapshot, command/test run, review, approval decision, runtime observation | supports/refutes criterion, validates task, changes code node, derived from run/task |

Stable code identity must use repository-relative path plus language-aware symbol identity (qualified name/kind/signature when available). Line/column ranges are refreshed from the current file version; line numbers alone are never graph identity. Store file content hashes and parser/indexer version. Never treat an LLM-invented edge as verified without source evidence.

## Implementation rules

1. Work Phase 1 through Phase 8 in order. Do not build the UI on unverified/mock graph data.
2. After each phase, update its checkbox/status with changed source paths, migrations, exact test commands/results, and remaining blockers.
3. Do not rewrite the existing CodeQ execution pipeline wholesale. Extend its project map, task persistence, tool/test/snapshot evidence, event stream, and sandbox boundaries.

5. Do not claim that multi-model collaboration inherently outperforms a larger model. Measure the selected model and graph workflow on repeatable project tasks.

## Research basis

- RepoCoder supports iterative repository-context retrieval rather than one broad prompt: [paper](https://arxiv.org/abs/2303.12570).
- Tree-sitter provides incremental syntax-tree parsing: [official documentation](https://tree-sitter.github.io/tree-sitter/).
- SCIP provides a language-agnostic code indexing protocol for definitions/references where an indexer is available: [SCIP](https://scip-code.org/).
- SQLite FTS5 provides local full-text retrieval without adding a separate search service: [official documentation](https://www.sqlite.org/fts5.html).
